## 二、这个项目要解决什么问题

求职时常见的两类困境：

1. **岗位要求看得懂，但没做过** —— JD 写着"熟悉 Redis 缓存、消息队列、分布式锁"，简历上却拿不出对应经历；
2. **HR 一问就卡壳** —— "以前有没有做过高并发？""这个项目你负责哪部分？"答不上来，因为确实没有可复述的实操。

本项目的做法：**每一条岗位要求 / HR 提问，都对应产出一个能跑起来、能验证、能讲清楚的最小项目**，而不是只写笔记。

```
收集岗位 JD 与 HR 提问
        ↓
解析出「技能点清单」（可验证的技术要求）
        ↓
对照自身现状，标注差距等级
        ↓
为每个差距设计一个最小可运行练手项目
        ↓
实现 → 机器验证 → 写结项说明（能回答 HR 的版本）
        ↓
归档到证据链，随时可复述
```

### 核心纪律（继承 XM01）

> **一次只推进一件事；每步必须有一次机器验证。**
> 禁止只写文档不写代码，也禁止只写代码不做验证记录。

## 四、命名与文档规范（继承 XM01）

1. **文档命名**：`主题-版本-日期`，如 `技能差距分析-v1-20261026.md`
2. **项目命名**：`P<序号>-<技能点>-<简称>`，如 `P01-AI获客`
3. **脚本编码**：`.ps1` 必须 UTF-8 with BOM；`.cmd` 必须 GBK
4. **中文输出**：脚本处理中文一律落盘 UTF-8 文件再读
5. **配置修改**：改完必须读回校验
6. **版本管理**：成品文档只增不改，修改升版本另存

## 五、证据链：如何回答 HR

每个练手项目完成后，必须能回答三个问题：

| 问题 | 对应内容 |
|---|---|
| "你做过什么？" | 项目目标 + 技术 + 代码位置 |
| "怎么证明做成了？" | 验证记录 + 看板 dashboard.html |
| "遇到过什么坑？" | 项目 README 的"问题与解决" |

> 面试官问"以前有没有做过 XXX"时，能立刻说出：**做过 → 代码在哪 → 怎么验证 → 踩过什么坑**。
